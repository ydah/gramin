文法ファイルの差分を読むとき、ルールの追加だけでなく、参照先や再帰の変化も追いたくなります。
graminは、文法の構造を数値にして変更の確認を助けるツールです。
Yacc系、BNF/EBNF、ANTLR4、Menhir、Peggyの5形式を共通のGrammar IRに変換し、ルール数や選択肢数、依存関係などを測ります。

## 小さな文法を測る

次の内容を `hello.bnf` に保存します。

```bnf
start ::= "hello";
```

```sh
npx @gramin/cli analyze hello.bnf --frontend bnf --format md
```

この例では、ルール数と選択肢数がともに1になります。
ルール別の出力にも、選択肢数や右辺の長さ、参照するルール数が入ります。
測れない値は0に置き換えず、`notApplicable` に理由を記録します。
0と「未測定」を区別したまま、JSONやCSVとして保存できます。

## Rubyのparse.yを二つの表現で測る

パラメータを受け取るルールでは、呼び出しごとに具体的な規則が変わります。
そこでgraminは、FIRST/FOLLOWやLL(1)、生のSLRを測るときだけ、ローカル定義のパラメータを展開します。
元の文法のルール数や依存構造は、展開前のIRで測り続けます。

固定したRuby開発版の `parse.y` には、18個のテンプレートを含む251ルールがあります。
測定用の表現では、233個の通常ルールに47個のパラメータ実体と28個のEBNF補助ルールを加え、308ルールを解析します。
出力には、展開の方針と上限、元のルール数と展開後のルール数を残します。
展開が上限に達した場合や必要な外部定義がない場合は、途中までの結果を完全な測定値として返しません。

この固定入力の生のSLR計測は、LR(0)状態数が1,440、shift/reduce衝突が4,911、reduce/reduce衝突が3,039です。
優先順位や結合性による解決を適用していないため、パーサ生成器の結果や `%expect` の宣言値とは照合できません。
入力のコミット、ハッシュ、展開の条件は[AtlasのRubyページ](https://ydah.github.io/gramin/atlas/ruby)で確認できます。

## 比較する前に測定の条件をそろえる

同じ言語を表す文法でも、繰り返しをEBNFで書くか、再帰で書くかによって構造の値は変わります。
graminは各指標に、厳密値かヒューリスティックかという分類と、比較に必要な条件を定義しています。
条件付きのB分類や形式に依存するC分類では、capabilityや展開方針などが合わない値を差分から除外し、理由を表示します。

保存した特徴量を比べる場合は、次のコマンドを使います。

```sh
npx @gramin/cli diff before.json after.json --features --format md
```

ルール別の差分は、名前で対応付けます。
追加と削除、各値の変化を出します。
改名は削除と追加として扱います。
数値の増加だけで文法の良し悪しを決めず、レビューで確認する箇所を探す材料にします。

## レビューとデータ分析に使う

GitHub Actionはmerge-baseの文法からベースラインを自動で測り、PRコメントを更新します。
手元では `analyze-many` とCSV出力で、複数の文法を表として扱えます。
[Grammar Atlas](https://ydah.github.io/gramin/atlas/)には12個の固定入力を収録し、Rubyの歴代リリースも並べています。
数値の推移は各ソースの観測結果であり、Lramaへの移行がすべての変化の原因だとは断定していません。

MCPサーバーは `analyze`、`diff`、`ir`、`digest` を提供します。
文法中のアクションや述語は実行せず、解析を時間とメモリの監視付きワーカーで動かします。
この監視はOSのサンドボックスによる隔離ではありません。
[ブラウザのサンドボックス](https://ydah.github.io/gramin/sandbox)でも、手元の文法を測れます。
元の表現と測定の条件を確認しながら、差分を読んでみてください。
